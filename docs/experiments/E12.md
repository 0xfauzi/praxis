# E12: does the pipeline give uniform p values when nothing can work?

## Why this matters (30 seconds)

Rule PR-1 reads one p value, the specific contrast, and trusts the pipeline placebo to
catch a leak. Both trust the whole chain from `praxis start task` to `praxis show
report`: the arm draw, the binding rule, the recorder's segment close, the probe
schedule, the exclusions and the randomization tests. A leak anywhere in that chain makes
a p value small with no effect. No amount of owner data can show the chain is sound,
because the owner's data always holds an unknown effect. A simulated owner who cannot
learn can show it. Under that null, every p the report prints must be uniform on [0, 1].

## Decision rule, written before the run (2026-10-19)

The rule is in the docstring of `experiments/E12/null_pipeline.py`, written before the
first run. For each test the report prints (specific, near, untargeted, pipeline placebo,
f1 shuffle), over the R runs where the report printed a number for it:

- KS: the Kolmogorov-Smirnov distance of its p values from Uniform(0, 1) is below the 5
  percent critical value, 1.3581 / (sqrt(n) + 0.12 + 0.11 / sqrt(n)) (Stephens 1974).
- Share: the count of runs with p < 0.05 lies inside the central 95 percent interval of
  Binomial(n, 0.05), from the exact binomial CDF. At n = 200 that interval is 4 to 16.
- Placebo: the count of runs where the pipeline placebo suspends the contrasts is at most
  that interval's upper end.

The rule binds the uniform responder, which is the null that the contract names. A
failure names the test and the leak it suggests. A share above the interval is a leak. A
KS failure with the share inside or below the interval is conservatism (ties or
discreteness in the statistic), not a leak. The general effect needs 3 repositories, and
each run has one. So its p is recorded as the report prints it, and it is not tested.

Two more responders were fixed before the first run, each with its expected result:

| Responder | What it does | Expected |
|---|---|---|
| `uniform` | Each answer uniform on 1 3 5 7 9, `s` at a rate of 0.1 | every test passes |
| `lean` | Knows nothing and leans to no: weights 0.35, 0.30, 0.15, 0.10, 0.10 | every test passes |
| `remembers` | Answers an item that it saw as a prequestion by its truth (9 or 1), every other item as `uniform` | specific fails with a share above the interval; the other four pass |

`uniform` gives the same Brier distribution for a true and a false item, because the grid
is symmetric. So a difference in truth rate between two item sets is invisible to it.
`lean` makes the Brier score depend on the truth, so such a difference shows only there.
`remembers` is a testing effect: it is the positive control, and it shows whether the
runner can see a real effect.

## What we did

`experiments/E12/null_pipeline.py` builds one temporary world per run and deletes it at
the end:

- A git repository with a flat package of 12 modules, `src/pkg/m01.py` to `m12.py`. A
  seeded layer order gives each later module a `from pkg import` line to each earlier
  module with probability 0.15. One commit.
- `praxis set components` at T0, Monday 2027-01-04. The mechanical map has 12 product
  components and 132 D1 items. The start week is drawn from 2027-W03 to W08.
- 60 tasks from 2027-03-01, 8 weeks after T0, so every start-week candidate has passed
  and every task is randomized. Three tasks a day, at 09:00, 11:00 and 13:00.
- Each task: `praxis start task`, answered by the responder. Then one agent segment,
  replayed through `praxis hook` with the Claude Code 2.1.303 payloads in
  `fixtures/claude/2.1.303`: UserPromptSubmit, PreToolUse Write, the file edit,
  PostToolUse Write and Stop. A SessionStart opens each day. The Stop closes the task,
  and the runner refuses a Stop that prints no notice.
- The segment edits one module, drawn uniformly. With probability 0.2 it adds a `from
  pkg import` line, otherwise a constant. The prompt names that module and a canary. A
  synthetic transcript entry in the 2.1.303 format holds it, so R1 and the f1 shuffle can
  be computed.
- Every evening at 20:00, `praxis test structure`, answered by the responder. An exposed
  item is first probed 7.3 to 7.5 days after exposure. Probing goes on for 8 days after
  the last task. Then `praxis show report --json`.

The clock. Every command runs as `praxis.cli.main` in a new interpreter with piped stdin
and stdout. That is what the `praxis` console script runs. There is one substitution:
`praxis.hooks.now_iso` returns the runner's simulated time. It is the clock that every
command and every hook reads at its start. The runner writes no ledger row: every row
comes from the binary. Two clocks stay real. task.py stamps forecast rows with the wall
clock, and the report never reads that stamp. Probe seconds are monotonic time, so every
answer meets the 60 s deadline.

`show report` had no machine-readable form. This experiment added `--json`
(`render.to_json`): the numbers, reason codes and assumptions of the text, unrounded,
with the same refused-word check. A test that cannot be computed is `null`.

Checks inside every run, beside the rule: each skip the responder typed is a NULL row in
the ledger and no other row is NULL; the canary of every prompt is absent from every byte
under `$PRAXIS_HOME` (invariant 5); every hook exits 0 with an empty stdout or the one
notice (invariant 7); no task is forced control.

Before the 200 runs, three trial batches (1 run of 6 tasks, 1 of 60 and 4 of 60) checked
the driver. They are not part of any result below. A first start of the uniform batch was
stopped after 4 runs, because a break-the-fix edit to `render.py` overlapped it, and the
runs import the working tree. It was restarted from a clean tree with the same seeds.

## What we rejected

- Calling the modules with their `now` arguments in one process. That skips the CLI, the
  argument parsing, the per-process ledger open and the hook's fail-open wrapper, which
  are part of the chain under test.
- Writing exposures and responses through store.py with explicit timestamps. A leak in
  task.py, probe.py or the recorder would then be invisible, because the runner would be
  the one choosing the rows.
- Running the real clock. The probe lag is 7 days and the start week is 2 to 7 weeks
  after the map is set, so a real-time run takes weeks per study.
- One responder only. The uniform responder cannot see a difference in truth rate
  between two item sets, so `lean` was added for that leak, and `remembers` to show the
  runner can see an effect at all.

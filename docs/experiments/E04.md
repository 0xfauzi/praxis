# E04: what do the design 03 recorder duties cost the hook the agent waits on?

## Why this matters (30 seconds)

Design 03 section 5 gives `praxis hook` new work: HEAD and the session base on every
snapshot, X1 import edges of the changed Python files at every Stop, the decision pointer,
and the read, outcome rows and notice at the Stop that closes a registered task. Every
millisecond is paid inside the owner's agent session, and over budget the edges become
`unobservable` (design 3.4). The question is whether that work fits beside the agent.

## Decision rule, written before the run (2026-10-19)

On a scratch clone of praxis's own tree, with a frozen mechanical map and a registered
task, the Stop that scans X1 edges and closes the segment must add at most 100 ms to the
wall-clock p95 of the same Stop without a frozen map, and all 20 such Stops must end `ok`
with `task closed` in their note. 100 ms is a tolerance chosen before the run, not a
measured bound. A second check is reported and is not part of the rule: the same Stop with
200,000 extra hook_events rows in the ledger, because hook_events has no index on
`session_id` and the base and HEAD-move reads scan it.

## What we did

`experiments/E04/hook_cost.py`, copied from `experiments/E01/hook_cost.py` and extended:
the installed binary, one process per event, 20 sessions per condition, wall clock around
each process and the `duration_ms` the hook recorded about itself.

- E01: the E01 five-event sequence on the small calc repository, rerun today on this
  container so the comparison is same-day.
- plain: `git clone --local` of praxis, SessionStart, UserPromptSubmit, Pre and Post Edit
  appending one line to `src/praxis/cli.py`, Stop; no frozen map.
- duty: the same with the mechanical map derived from the clone (14 product components at
  the cloned HEAD) frozen, and a task registered through `store.task_register` before each
  prompt, so the prompt binds it and the Stop scans `cli.py` and closes it.
- big: duty again after 200,000 synthetic hook_events rows from other sessions.

## What we measured

Wall clock in ms, then the hook's own `duration_ms` (inner), n = 20 per cell:

| condition | Stop wall p50 | Stop wall p95 | Stop inner p50 | Stop inner p95 |
|---|---|---|---|---|
| E01 (calc repo) | 99.4 | 115.5 | 13.6 | 17.9 |
| plain (praxis, no map) | 96.0 | 104.7 | 13.8 | 17.5 |
| duty (map, task closes) | 129.4 | 150.8 | 39.2 | 46.3 |
| big (duty, 200k rows) | 178.7 | 243.2 | 96.7 | 133.7 |

- Added Stop wall p95, duty minus plain: 46.1 ms. All 20 duty Stops ended `ok` with
  `edges: 5 in 1 files; task closed`. Rule: PASS.
- Other events are unchanged by the duties: duty SessionStart, UserPromptSubmit,
  PreToolUse and PostToolUse inner p50 13.5 to 14.5 ms, against 11.7 to 13.9 ms plain.
- With 200,000 hook_events rows: UserPromptSubmit inner p50 45.6 ms (13.5 without),
  PreToolUse 27.8 ms (13.7), Stop 96.7 ms (39.2). The cost is the unindexed scans.
- The E01 condition today: wall p50 95.8 to 101.5 ms per event, against 69 to 74 ms on
  2026-10-18. The same script on the same repository, so the 25 ms is the container, not
  praxis; comparisons here are within one run.

## What it means

The new duties fit: the segment-closing Stop costs about 25 ms more in-process and 46 ms
more at p95 wall clock on praxis's tree, far inside the 10 s hook timeout and the 20 s
watchdog, and the X1 scan never went unobservable. The cost that grows is not the new work
but the ledger: every snapshot event now reads hook_events by session, and without an
index that read is linear in the ledger's lifetime.

## What we rejected

- Scanning X1 over the whole tree at every Stop. Wave 1 measured it at p50
  71.6 ms on praxis; the file-grain scan of the touched files resolves against the whole
  tree for about a tenth of that, and only files the agent changed can have changed edges.
- One `static_imports` call per touched file. Exact but linear in files; the recorder
  scans all touched files in one call with each file as its own node, and rescans alone
  only a file that imports another scanned file, so one statement naming two files of one
  component still counts one site.

## How sure we are

- Measured on this container, one Python file touched per segment. A segment touching
  many Python files costs one extra scan per file that imports another touched file; that
  count needs measuring on the owner's sessions.
- 200,000 rows is a size chosen for the check, not a measured ledger: what the owner's
  ledger reaches after months needs measuring (`praxis show status` can count it). The fix is
  an index on `hook_events (session_id)` in store.py, which this stage may not edit.
- The wall clock includes about 80 ms of interpreter and package start-up, as in E01.

## What downstream may now say

- "X1 edges at Stop and the segment close add about 46 ms at p95 on praxis's tree."
- Not yet: any figure for repositories larger than praxis, or for an old ledger before
  hook_events gains its session index.

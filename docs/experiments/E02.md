# E02: can agent-authored spans be recovered from the ledger's hashes alone?

## Why this matters (30 seconds)

The recorder stores hashes, never lines (AGENTS.md invariant 5). A drill item is a
function the agent wrote. If the instrument cannot find that function from hashes against
the file as it stands today, either the privacy rule or the instrument has to give.

## Decision rule, written before the run (2026-10-18)

Replay the recorded Edit through the real recorder against a real repository, then hash
every line of the current `pkg/calc.py` as a `+` line and look it up among the agent
deltas. The mechanism is fit if (a) exactly the three lines the agent added are flagged
and nothing else, (b) the same three line numbers are flagged after the owner appends a
function below them, and (c) the flagged span lies inside exactly one function by `ast`.
Any other result and the instrument needs a different source of items.

## What we did

`experiments/E02/span_recovery.py`: a fresh repository with the fixture's `originalFile`
committed; `praxis hook` driven with the recorded PreToolUse and PostToolUse Edit bodies
around the recorded edit; `agent_deltas` read back; the current file hashed line by line
with `praxis.gitdiff.line_hash(b"+", line)`; `ast.parse` for function spans.

## What we measured

| Check | Result |
|---|---|
| lines flagged after the edit | 12, 13, 14 |
| lines flagged after the owner appends `owner_added()` | 12, 13, 14 |
| functions by `ast` | add 6-8, divide 11-15 |
| function containing the flagged span | divide, and only divide |

All three clauses of the rule held; the script's own assertion passed.

## What it means

Line hashes are enough to find the agent's work in the live file, and the line numbers
follow the file (the lookup is by content, the position is read off the current file).
docs/design/02-instrument.md builds candidate items on exactly this.

## What we rejected

- Storing the agent's patch text to locate items later. Not needed, and forbidden.
- Locating by line number recorded at edit time. Line numbers move with every later edit;
  the content hash does not.

## How sure we are

- Measured, on one recorded Edit of one file. A line the owner later retypes identically
  to an agent line will be flagged as the agent's; that is the first assumption on every
  item row and it cannot be removed by this mechanism.
- Not measured: files with many identical lines (blank lines are the common case: a blank
  line the agent added is indistinguishable from any other blank line, so a function's
  agent fraction can be inflated by blank lines). Needs measuring on the owner's
  repositories before the fraction threshold is set in docs/preregistration.md.

## What downstream may now say

- "Items are functions whose current lines match agent deltas by content hash."
- Not yet: any fraction threshold as more than a recorded default.
- The write-it item this served was rejected (docs/design/03-measurement.md). The
  content-hash lookup is reused, as a multiset lookup, for decision survival and detection
  latency.

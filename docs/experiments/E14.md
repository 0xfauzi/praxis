# E14: can praxis plant a fault at a known altitude and get its label back?

## Why this matters (30 seconds)

Design 05 proposes a criterion above P1: the owner is shown changes that praxis planted
in a scratch copy, some wrong and some clean, at five altitudes (constraint, flow, edge,
mechanism, form), and says how likely each is to be wrong. The design stands or falls on
the generators. A planted fault must be invisible to a parse and an import, or it is
caught without any model. Its label (level, component, wrong or clean) must be fixed
without a judge or a project test, or invariant 9 is broken. And each repository must
supply enough items at each level, or the level cannot be measured there. E14 measures
those three things on three real repositories, before any card is shown to anyone.

## Decision rule, written before the run (2026-10-25)

The rule is in the docstring of `experiments/E14/faults.py`, written before the first
run and amended once before the first counted run (below). In short, per repository and
per level, over up to N = 20 drawn faults and 20 drawn decoys (seed 20261025):

- (a) Valid: the mutated file parses; the mutated module imports whenever its base
  imports; for `c_drop_check` the DDL still executes; for `f_drop_call` every scenario's
  exit code is unchanged. An item whose base module does not import is import-unknown,
  neither valid nor invalid.
- (b) Recovered: re-extraction on the mutant gives the planted label and nothing else
  (X4 hook matches, X4 CHECK counts, X2 traces, X1 edges and cycle status, or AST
  locality, by level).
- A level PASSES when at least 90 percent of drawn faults and of drawn decoys with a
  known import are valid and every valid item is recovered. It is SUPPLIED when it passes
  and its estimated valid supply (distinct items times the valid share) is at least 20
  faults and 20 decoys. It is UNDETERMINED where no extractor can check its label. E14
  passes iff no level on any repository has a recovery failure (FAIL_B).

Prediction, written before the run: praxis supplies L1, L3, L4 and L5 with L2 checkable
by the design 03 section 3.2 scenarios; telltale supplies L1, L3, L4 and L5 with L2
undetermined; systemap supplies L3, L4 and L5, with L1 supply 0 and L2 undetermined.

## What we did

`experiments/E14/faults.py` (runner), `edit.py` (byte-offset splicing, the function
table), `sites.py` (X4 hooks and the L1 relocation operators), `ddl.py` (X4 CHECK
clauses, read at runtime), `ops.py` (L2 to L5 operators), `flow.py` (X2 in the E14 clone)
and `praxis_scenarios.toml` (the four scenarios of design 03 section 3.2, verbatim).
Standard library only. For each repository, at its committed HEAD:

- One `git clone --local` under a temporary `$PRAXIS_HOME`, with no remote and git hooks
  off; deleted at exit. The owner's tree and `.git` are only read by the clone.
- The mechanical component map (`components.derive`), X1 over the clone, the scoped
  pygrep hooks, the DDL modules, and, on praxis, two base traces of each scenario.
- Every candidate site of every operator, enumerated. Then a seeded draw of up to N per
  side per level, round robin over the level's operators.
- Each item: the mutant is written over the file, the checks run, the base bytes are
  written back, and the run stops unless `git status --porcelain` is empty. No bytecode
  is written anywhere (`PYTHONDONTWRITEBYTECODE`), so a mutant of the same size and mtime
  second as its base is never read from a stale `.pyc`.
- Output: component ids, paths, hook ids, table names, operator names, qualified function
  names and counts. No code text is printed or stored; DDL text never leaves the probe
  subprocess (only counts and offsets cross the pipe).

Three trial runs at N = 3, and one at N = 2 after a refactor, came first. They are not
results. Each trial showed a defect, and each fix is an amendment in the docstring, made
before the counted run:

1. Trial 1: the AST-literal DDL reader found 0 tables in praxis (19 literals, all
   fragments of one f-string, all failed to execute). DDL is now read at runtime by
   importing the module in the clone (`ddl.py`). L2 found only 3 candidates, because
   calls on typed parameters (`store.write(...)` on `store: Store`) did not resolve;
   annotations now resolve them (amendment 4).
2. Trial 2: 3 telltale items (in 2 modules) and 1 systemap item failed a direct import of
   their base module with a circular-import error; the program imports them only after
   its entry module. The import check now falls back to the console-script module first
   (amendment 1). 4 of 6 module-level L3 back edges on praxis broke the import, which
   makes the fault visible and makes placement leak the label; L3 now places the import
   inside a function for faults and decoys alike, and still import-tests the
   module-level form on every item, reported only (amendment 2). 3 of 3 L2 items guessed
   as faults (their component pair was a call edge in a base trace) left every trace
   unchanged. A positive control (`hooks.run` returning at once) moved the call-edge sets
   of both hook scenarios, so X2 sees a real change; the guess was wrong. L2 is now
   labelled by X2 after the mutation, recovered when a second trace agrees (amendment 3).
3. Trial 3: 1 of 3 praxis `c_drop_check` items failed recovery: the removed clause sat in
   a fragment that several tables share. 12 of the 64 clauses whose text is unique in
   `schema.py` are such fragments. A clause is now removed only when its text is also
   unique in the runtime DDL (amendment 5).

The counted run used the files whose hashes were recorded before it started; they were
unchanged after it. One later edit corrected amendment 1's wording (it said "3 telltale
modules"); no code changed.

`experiments/E14/layer_rule.py`, a descriptive supplement written before its first run,
asks how much of an L3 item the layer order alone answers. Its first run counted
components with no Python file, so its systemap pool (349 decoys) differed from the one
`faults.py` draws (195); the pool was aligned and the run repeated.

Every failure and every unknown:

- 2 invalid items, both `c_drop_check` with `ddl_fails`: praxis table `attributions` and
  telltale table `evidence`. Removing the clause left DDL that no longer executes, so the
  mutant would be visible. The removal rule (comma and whitespace handling) is the
  suspect; not investigated further.
- 12 import-unknown items, whose base module failed both import modes: telltale
  `forecast/timesfm.py` (3 items; it imports `torch`, which the collector environment
  does not install, by design), and systemap's TypeScript modules (9 items).
- 0 recovery failures in 471 drawn items (188 praxis, 163 telltale, 120 systemap).

Detail behind the verdicts:

- L1. Every praxis candidate comes from `derived-writes-only-in-store` (4 guarded
  statements in `store.py`, each relocatable into 21 components). `judge-isolation` has
  no instance to relocate, because `judge.py` does not exist. On telltale,
  `forecast-isolation` gives 2 statements and `resanitize-is-the-only-update` 1;
  `derived-writes-only-in-store` gives 0, because no line of telltale's `store.py`
  matches its pattern. The decoy side is one item per guarded statement, so it is 4 on
  praxis and 3 on telltale.
- L2 (praxis). All 24 call sites were drawn. X2 labelled 1 a fault (in `Store.open`, a
  call from `store` into `schema`) and 23 decoys, and a second trace agreed on all 24.
  The pair guess said fault for 15 and was right for 1; it said decoy for 9 and was right
  for 9. Dropping one call site rarely changes a component path, because a component
  call edge aggregates every call site between the two components.
- L3. Module-level placement, import-tested on every drawn item: faults that still
  import are 5 of 20 on praxis, 17 of 20 on telltale and 20 of 20 on systemap; decoys
  import 20 of 20 everywhere. Back-edge faults come from few source components: 21 on
  praxis, 3 on telltale, 6 on systemap. 10 telltale L3 items needed the entry import mode.
- Layer rule (supplement). Layer-incongruent decoys (the layer order calls them wrong):
  73 of 273 on praxis (0.27), 0 of 53 on telltale, 0 of 195 on systemap. The rule's Brier
  score is 0.01 on every fault, 0.224 on praxis decoys and 0.010 on telltale and systemap
  decoys.

Predictions against results: L1 was predicted supplied on praxis and telltale and is not
(faults yes, decoys 4 and 3). L2 on praxis was predicted checkable; it is, but it
labels 1 fault in 24. Everything else was as predicted.

## What it means

- The generators are sound where they produce items: no drawn item's label disagreed with
  its re-extraction, 2 of 471 were visibly broken, and 12 could not be checked for an
  import. E14 passes its rule.
- L3, L4 and L5 are supplied on all three repositories. L4 and L5 supply is in the
  hundreds to thousands of functions; it is never the binding constraint.
- L1 has faults and lacks decoys. The in-site decoy gives one item per guarded statement.
  A repository with machine-readable constraints still gives L1 only on the fault side,
  and a repository without them (systemap: 12 prose invariants, 0 import rules, 0
  scoped hooks, no DDL) gives nothing. L1 needs a second decoy operator (design 05, Q2).
- L2 at component grain labels almost nothing a fault. The X2 tracer records component
  pairs, so it cannot see one dropped call among several. A function-grain trace
  (caller function to callee component) is the named fix (design 05, Q3).
- On telltale and systemap the layer order answers every L3 item, because every decoy
  there is layer-congruent. L3 catch skill beyond layering can be scored only on
  layer-incongruent decoys, and only praxis has them (73). That is design 03's R_layer
  finding again, one level up.
- A back edge an agent adds at module level often breaks the import on its own on
  praxis (15 of 20) and almost never on systemap (0 of 20). Where it breaks, the agent's
  own run shows the fault, and an owner's catch adds little; where it does not, only a
  model of the layering catches it.

## What we rejected

- Reading DDL from string literals in the AST: 0 tables on praxis, whose schema is one
  f-string with helpers.
- Labelling L2 by whether the component pair is a base call edge: wrong for 14 of 15
  fault guesses in the counted run, after 3 of 3 in a trial.
- Module-level L3 placement as the counted form: it breaks imports on praxis and leaks
  the label through placement.
- A per-mutant fresh clone: one clone per repository with byte-exact restore and a
  `git status --porcelain` check after every item is cheaper and checks the restore.
- Running project tests on a mutant: invariant 9, and design 03 dropped mutation
  localisation for scoring by test names.

## How sure we are

- 20 of 20 valid gives a one-sided 95 percent lower bound of 0.86 on the valid share
  (0.05^(1/20), exact). The 90 percent threshold is met as a point estimate, not
  established.
- 0 recovery failures in 471 items bounds the failure rate below about 0.0064 (rule of
  three), treating items as exchangeable, which they are not across levels.
- Decoy equivalence is by construction and was not checked behaviourally outside L2.
  `m_mirror_compare` assumes consistent comparison methods on the operands;
  `l_rename_local` assumes no dynamic access to local names beyond the forms it refuses.
- A fault that changes nothing observable (an inert fault: dead code, a bound never
  reached) is still labelled wrong. Its share was not measured (design 05, Q4).
- Nothing about presentation, the owner, or whether planted faults resemble the agent's
  real faults was measured. No card was shown to anyone.
- One seed per repository; the L2 result on praxis is exhaustive (all 24 sites).

- "On praxis, telltale and systemap, the generators for L1 faults, L3, L4 and L5 produce
  items whose label an extractor recovers on the mutant, with no recovery failure in 471

- "L1 cannot be graded on systemap: it declares no machine-readable constraint. On

- "At component grain, dropping one call changes a named scenario's path in 1 of 24

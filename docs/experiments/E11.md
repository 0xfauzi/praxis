# E11: can the owner's existing transcripts supply the Stage 2 counts for Q1, Q3 and Q15?

## Why this matters (30 seconds)

The plan for Stage 1 was a pilot of three calendar weeks. Most of the supply counts that
the pilot collects are already on disk: the agent writes a transcript for each session.
These counts are human prompts, prompts that led to a change, repositories, structured
decisions, sessions and the empty-segment rate. If praxis can count them correctly from
history, Stage 2 can take these cells from history on the first day. This experiment
checks the counting method. The owner's machine is the population. This container is
the method check only.

## Decision rule, written before the run (2026-10-19)

The runner is `experiments/E11/history_supply.py`. It passes when all four hold:

- A1. On a frozen copy of `~/.claude/projects/*/*.jsonl` (the E08 population),
  `supply.measure` gives the same counts as the E08 runner on the same copy. The
  compared fields are files read, human-typed prompts, AskUserQuestion calls and
  ExitPlanMode calls. The earliest week of the window must be unobservable, so that the
  window holds every prompt.
- A2. The decision and session counts equal the E08 write-up: 0 AskUserQuestion, 0
  ExitPlanMode, 1 file. The transcript is live, so human prompts grew after E08. They
  are compared under A1 only.
- A3. A second run of `measure` on the frozen copy, with the same `now`, gives the same
  result. The registration denominator (`mutating`) is then reproducible.
- A4. The JSON output contains no path, no repository name and no cwd from the files.

## What we did

1. Wrote `src/praxis/supply.py`. It reads each transcript through `praxis.transcript`
   and keeps counts, ISO week labels and hashed repository ids. `praxis show supply
   [--weeks N] [--json]` prints the counts. The command writes no file.
2. Defined each count before the run:
   - A human prompt has `origin.kind` human. A session in which no prompt carries
     `origin` is unrecorded: its prompts have an unknown kind.
   - A segment runs from a human prompt to the next human prompt. A prompt of another
     kind (a task notification, a peer message, command output) does not end it.
   - `mutating` counts human prompts whose segment holds a call to a tool in
     `recorder.MUTATING_TOOLS`. This is the registration denominator of design 5.3.
     `bash only` is the part of it whose only mutating calls were Bash.
   - `subagent only` counts segments with an Agent or Task call and no mutating call.
     `empty` counts segments with neither. The empty-segment rate is empty divided by
     human prompts (design Q15).
   - A repository is the hashed git root (`gitdiff.repo_id`) of the cwd on the prompt's
     own line. A cwd that is not in a git repository on this disk is counted apart.
   - A week that ends before the first prompt on disk is unobservable, not zero.
3. Tested the module through the installed binary on a synthetic transcript directory
   with the 2.1.303 field names (`tests/integration/test_supply.py`). The expected
   counts were written before the run.
4. Ran the runner on this container on 2026-10-19 at 22:21 UTC, with an 8-week window.

Design 5.3 counted the first 18 human prompts of this same transcript. It found 7 with
no mutating call, 5 with Bash only and 6 with an Edit or Write. The supply module gives 6, 6
and 6 for the same 18 prompts. The one difference is the 18th prompt, which is Bash
only now. Its segment ran from 10:49 to the next human prompt at 11:58, and design 5.3
was committed at 12:02. If the segment was still open, with no Bash call yet, when the
design count was made, both counts agree. This explanation is reasoned, not measured.

## What it means

- The method counts what E08 counts, on the same bytes, and gives the same answer twice.
  History can supply these Stage 2 cells: decisions per week (Q3), human prompts,
  the registration denominator and repositories per week (Q1), and the empty-segment
  rate (Q15). These numbers must come from the owner's machine, not from
  this container.
- This container is not the owner's work. One orchestration session drives it, and in
  2026-W43 the agents wrote code in subagents and worktrees. So 17 of 18 mutating
  prompts that week were Bash only. An interactive week on the owner's laptop can have
  a different split.
- Bash only is the largest part of the denominator here (22 of 29). Bash counts as
  mutating because the recorder snapshots around it, but many Bash calls change no
  file. The denominator is therefore an upper bound on prompts that led to a recorded
  change. The recorder's agent deltas on the owner's machine give the exact count.

## What we rejected

- Reading Codex rollouts. Praxis has no Codex transcript reader, and no rollout exists
  here to check one against. The command counts rollout files and says that it did not
  read them.
- Counting a prompt with no `origin` as human. In the 2.1.302 and 2.1.303 session here,
  each such prompt carried `isMeta`, was a compaction summary, or started with a command
  tag. In an unrecorded session the kind is unknown, and the count says unknown.
- Taking the repository from the project directory name. The name is the cwd with `/`
  replaced by `-`, which cannot be reversed. The cwd on the prompt's own line is used.
- Reading subagent transcripts. A subagent's edits are not human prompts. A segment with
  only a subagent call is counted apart, as `subagent only`.

## How sure we are

- The equality with E08 is exact for the fields both runners count, on one file.
- The segment kinds have no second implementation to compare with. The integration
  test checks each kind on a synthetic transcript. Each of five deliberate faults in the
  module made the test fail:
  - a segment that any prompt ends;
  - every session treated as one that records origin;
  - Bash counted as a file tool;
  - weeks before the first prompt counted as zero;
  - the first cwd of the session used for every prompt.
- A worktree is its own repository, as in the ledger. On the owner's machine, a session
  in a worktree adds a repository id.
- The agent can delete old transcripts. A week before the first prompt is unobservable.
  A week after it is counted as complete, which is correct only if the owner deleted no
  transcript by hand.

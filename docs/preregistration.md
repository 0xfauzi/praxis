# Pre-registration

Status: DRAFT, Stage 1 not yet frozen. No task, probe or forecast row exists. Stage 1
(the day-zero package of 1.3) must be complete before the first such row is stored, and Stage 2 (confirmatory,
generated by experiments/prereg/derive.py) before the first randomized task (AGENTS.md
invariant 11). Measurement design: docs/design/03-measurement.md.

This file is Stage 1. It fixes what Stage 1 collects and from where, the design
choices the study runs under, the parameters `derive.py` will set and from what, every
validity check with its threshold and the plan it triggers, and the rule that Stage 1 data
never enters a confirmatory test (design section 9). Stage 2 is written later by
`derive.py` from the Stage 1 sources and committed before the first randomized task; section 2
fixes its frame now. After Stage 1 is frozen, every edit to this file says why in the same
commit, and the amendment log at the end records it.

## 1. Stage 1: the day-zero package

### 1.1 The questions the study will answer

Stage 1 answers neither question. It exists so that Stage 2 can answer them with
parameters fixed from measurement.

- Q1 (instrument): does predicting before the agent acts (a component forecast plus
  prequestions on items bound to the task by a rule identical across arms) lower the
  owner's delayed, unassisted Brier score on those structural items, against registration
  with the same feedback and no prediction?
- Q2 (policy, after Q1's validity checks pass): does running the agent in a per-prompt
  mode change P1 on the components the policy fired for?

### 1.2 Design

- Single participant. Q1: task-level randomization inside `praxis start task`,
  P(treatment) = 0.5 (design choice), seed committed in Stage 2; general effect by a
  multiple baseline across at least 3 repositories with randomized start weeks
  (Koehler-Levin), descriptive only if fewer repositories are active. Each repository
  draws its start week at its first frozen map, and its tasks before that week are
  control tasks (design 6.4). Q2: an allocation whose smallest attainable p is
  below alpha (unrestricted 4-of-8, at least 12 pair-blocked weeks, or multiple baseline);
  8 pair-blocked weeks are withdrawn (minimum p 0.0625).
- Stage 1 is a day-zero package (1.3), not a calendar pilot. The one sitting is practice
  and never a floor; no Stage 1 row enters a confirmatory test (1.9), and the internal
  pilot of 1.3.5 reads the arm column of no row.
- Carryover is assumed, not tested away: learning does not wash out.

### 1.3 What Stage 1 collects, and from where

Stage 1 has no calendar pilot. A week-long pilot was the first plan; most of what it would
collect is available on day zero, and the rest needs more calendar time than a pilot gives
and belongs to the study. Stage 1 is the day-zero package below, and Stage 2 is written by
`derive.py` from it. Each Stage 2 cell names its source here, so no cell is filled from
data that the confirmatory test later reads, except by the one rule in 1.3.5.

Prerequisite: the recorder fixes of design section 5 (apply_patch, base-sha diffing,
prompt_id and turn_id, edges at Stop) are installed before the first task row. Nothing
recorded before them is Stage 1 data.

#### 1.3.1 History: the owner's existing transcripts (E11)

`praxis show supply` reads the transcripts the agent already wrote on the owner's machine
(design Q3's population) and prints counts only, per ISO week and in total: human prompts,
prompts followed by a mutating tool call before the next human prompt (the registration
denominator, design 5.3), distinct repositories as hashed ids, structured decisions
(AskUserQuestion, ExitPlanMode) with their option counts, sessions, and the empty-segment
rate (Q15). `docs/experiments/E11.md` is the method check on this container; the owner's
machine is the population. It supplies: the registration rate, tasks and sessions per week,
repositories active per week, the S3 decision supply and the empty-segment rate.

History also supplies R1's inputs. R1 reads a segment's prompt and the components its
earlier segments touched (design 4.4), and a transcript holds both without a task row: the
files a mutating tool call named map to components through the frozen map. The R1 burn-in
and W_touch rules of 1.7 read these historical segments in place of closed tasks
[proposed, needs owner decision: `derive.py` reads closed tasks today and must learn to
read history segments through `praxis.supply`; until it does, the 1.4 value stands].

#### 1.3.2 One sitting: the owner answers the instrument once (E07's runner)

In one sitting of at most one hour the owner, with no agent attached, answers the P1
structural items of one repository with a frozen map at the grid, and one validation set
twice at least ten minutes apart. E07's runner reports seconds per item, per task and per
day from the rows. It supplies: the probe deadlines (response-time distribution), the
seconds per validation item that the N_VALIDATION rule needs, the V9 cost check, and format
practice. It also gives a per-item Brier SD at lag 0, which is a prior only: items answered
at lag 7 may spread differently, and 1.3.5 says what replaces it.

#### 1.3.3 Mechanical checks: no owner time

- V2: X1 static edges against X2 runtime traces of the owner's named scenarios
  (`praxis run scenarios`), per component.
- V3: the mechanical map against the owner's `praxis set components` map, per repository,
  as grouping purity in both directions (E03b's measure). The hand-labelled week of the
  owner's changes is withdrawn: the owner map is the hand label.
- V4: not a gate (1.7). The SWE-bench prior stands.

#### 1.3.4 The null pipeline: the pipeline's soundness (E12)

`experiments/E12/null_pipeline.py` drives the real binary end to end with a random
responder on a generated repository, R runs of T tasks, and tests that every p the report
prints is uniform under the null, that the share of runs with any p below 0.05 sits inside
the binomial interval around 0.05, and that the placebo suspends in no more than that
share. A failure names the test and the leak it suggests. This is the criterion for the
pipeline, not for the owner: it can show a leak in the scoring, the binding or the
randomization test; it cannot show anything about owner behaviour, real agent segments or
the lag in real time. E12 passes before Stage 2 is committed, and again after any change to
`scoring.py`, `report.py`, `task.py` or `probe.py`.

#### 1.3.5 The study's first weeks: an internal pilot, blind to arm

Four inputs need calendar time: the between-week SD of P1, its lag-1 autocorrelation, the
ICC of forecasts within a task and the per-item SD at lag 7. They size the study and set
nothing else. Stage 2 therefore fixes the task count by a committed re-estimation rule
(Wittes and Brittain 1990: an internal pilot re-estimates variance from the trial's first
part without reading the treatment contrast, and those observations stay in the final
analysis): after the first two ISO weeks with five or more first probes each, `derive.py`
recomputes the power simulation of 1.7 from these four inputs pooled over both arms, with
the arm column unread, and the Stage 2 task count takes the result once. The effect size is
never an input or an output of Stage 1: the minimum detectable Delta_spec is a simulation
result, and the effect itself is Stage 2's.

A parameter that defines the outcome keeps its 1.4 value when its input needs calendar
time: L stays 7 days, L_max 28 days, the binding and preview window W, the detection
window W_d and the decision survival threshold keep their Stage 1 values. The study reports
the statistic that would have set each (the L = 2 against L = 7 comparison on exposed items,
`probe_missed` by lag, the registration-to-prompt gap, S4 latency, S3 survival) as
descriptive output, and a change is an amendment that opens a new epoch (design 3.5), never
a mid-study edit.

Collected from the first task row on, in every repository with a frozen component map:

- Recorder rows: snapshots, agent deltas, attributions, edge history at Stop, decision
  pointers, hook latency.
- Component maps and pool supply: `praxis set components` and `praxis show components`
  per repository.
- Tasks: registration time, arm, sampled components, F1 forecasts, prequestion answers, the
  bound, related-untested and drawn-not-shown items, flags, seconds spent, abandonment.
- P1 probes: every first probe of an exposed item, with response time, deadline result,
  truth, coverage and the attached-agent result; a validation-only set probed twice, 7
  days apart (V1). Validation rows carry no lag by schema.
- S1 drift probes weekly, S2 boundary rules and divergences, S4 removals, S3 decision
  pointers and responses where structured decisions occur, K knockouts for V7. C1
  Pathfinder runs are stored as PFSIM and PFSIM minus chance against the X1 referent,
  with the component count (`scoring.pfsim`, which replaced the unchecked closeness
  formula of design Q13); the ratings themselves are discarded.
- Owner-machine measurements, reported by `praxis show status` and `praxis show supply`:
  repositories active per week, structured-decision supply, empty-segment rate, Codex
  payloads. Nothing is blocked on them.

### 1.5 Metrics and definitions

Grid {0.1, 0.3, 0.5, 0.7, 0.9}; Brier per item; skill against references fitted on prior
data only (R_base, R_layer, R_fam for P1; R1, R0, R_last for F1), NULL until fitted;
Murphy decomposition with the Ferro-Fricker correction; CORP diagrams, bins read only at
81 or more forecasts; component map frozen per repository before its first task,
versioned, never pooled across versions; unassisted means the attached-agent check passed
and the item deadline was met. Stage 2 fixes, each from derive.py and starting from the
values in 1.4: L, L_max, deadlines, r, k_e, k_r, k_p, h, windows W, W_d and W_touch,
N_VALIDATION, the survival threshold, the exclusion cap and minimum counts. No Glicko-2, Elo or Rasch: one respondent
cannot identify item difficulty.

#### Interval level for V5 and V8 [proposed, needs owner decision]

A 90 percent two-sided percentile interval by cluster bootstrap over tasks, because
forecasts within a task are not independent. B = 2000 resamples, seed committed in Stage
2. "The interval excludes zero" is then the one-sided test at alpha 0.05, the level fixed
in 1.4, so the validity checks and rule PR-1 use one error rate.

### 1.9 Stage 1 data never enters a confirmatory test

No row of the one sitting, and no history count, is an observation in any Stage 2 test,
estimate or decision rule. Stage 1 data sets parameters through `derive.py` and nothing
else. An item exposed or probed in the sitting is consumed and is re-admitted only when its
truth flips (a new epoch, design 3.5). Validation-only items are excluded from every
confirmatory analysis. The sitting is never used as a floor or a baseline. The internal
pilot of 1.3.5 is the one exception, and it is bounded: its rows stay in the confirmatory
test, it sets the task count only, and it reads the arm column of no row.

## 2. Stage 2: confirmatory (generated by derive.py, not yet written)

Stage 2 is generated by `derive.py` from the Stage 1 sources (1.3.6) and committed before
the first randomized task. It fixes the outcomes, estimands, allocation, tests, alpha, seeds,
exclusions and decision rules. The frame below is fixed now; Stage 2 fills its numbers and
may narrow it, never widen it.

### 2.1 Outcomes

Primary (Q1): Delta_spec, mean Brier of first delayed P1 probes on bound items in control
tasks minus treatment tasks, items with unchanged truth and deadline met. Secondary, in
this order and no others: (1) near transfer, the same contrast on related-untested items;
(2) untargeted effect, the same contrast on drawn-not-shown items; (3) general effect,
multiple-baseline level change in never-exposed P1 Brier; (4) F1 forecast skill over R1;
(5) S1 drift-notice skill; (6) S2 caught share (associative); (7) task and probe
completion rates; (8) substitution rate by judge, deferred until a judge exists. Q2
primary: P1 on components the policy fired for.

### 2.2 Thresholds and decision rule

Rule PR-1 (Q1): the instrument is said to have changed delayed structural accuracy on
bound items only if the one-sided randomization test of Delta_spec (per-task mean Brier as
the unit, arms re-drawn under the actual allocation rule, seed and draw count committed)
gives p below alpha (0.05, fixed in 1.4), the pipeline placebo does not differ from zero,
and V1, V5 and V6 passed in the pilot. The minimum detectable Delta_spec is written here
from simulation through this exact test using pilot per-item SD, ICC, between-week SD,
lag-1 autocorrelation, registration rate and item supply; a repository whose supply cannot
reach the simulated count is excluded from the confirmatory analysis. Rule PR-2 (Q2) is
written in Stage 2 in the same form. A report that meets a rule may say changed under rule
PR-1 (or PR-2); cause, impact and would stay refused.

### 2.3 Signal admission (calibration)

A behavioural signal may enter any report or policy decision only if:

- Fit on the first half of available weeks, it predicts the held-out second half's P1
  score per component with a correlation whose confidence interval excludes zero. Stage 2
  fixes the interval level and the minimum number of held-out weeks.
- It fails to predict P1 scores on shuffled week labels (the placebo in 2.4).

Admission is a commit that cites both results. A signal that later fails on new weeks is
removed by a commit that cites the failure.

### 2.4 Placebo and permutation

- Placebo: every calibration and every primary analysis is repeated with labels shuffled
  (seeded, exact enumeration when there are 70 or fewer allocations, otherwise Monte Carlo
  with a committed draw count, seed committed in Stage 2). A result that is not
  distinguishable from the shuffled distribution is reported as such. The placebos:
  drawn-not-shown against never-drawn items; F1 forecasts shuffled among tasks; component
  labels permuted on the truth graph.
- Randomization test for each primary outcome: the observed contrast against its
  distribution under re-drawing the allocation by the rule actually used (tasks for Q1,
  start weeks for the general effect, the Stage 2 allocation for Q2).

### 2.5 Exclusions, fixed before data

- Weeks with fewer than N sessions are excluded from the primary analysis. N is set by
  derive.py from the pilot's session counts.
- A probe answered with an agent attached is void and is logged, and the refusal counts
  against probe completion rate.
- Tasks flagged agent_previewed, late_prediction or version_change are excluded from F1 up
  to the pre-registered exclusion cap, beyond which they form a sensitivity stratum; items
  answered after their deadline are excluded from the primary.

### 2.6 What this design can and cannot show

It can show whether this participant's delayed structural accuracy on bound items differed
between tasks in which they predicted and tasks in which they did not, and, for Q2,
whether P1 moved differently under the policy, each under its rule. It cannot show an
effect size for anyone else. Task-level randomization estimates the effect of being asked
to predict; the effect of probing itself is applied equally to both arms and cannot be
estimated. The protocol in 2.7 is how the first limitation is addressed over time.

### 2.7 Protocol

The instrument, this file and an anonymized export schema (strips paths, identifiers and
code; keeps per-week metrics and scores) are published so that another person can run the
same pilot and confirmatory study on their own machine and produce comparable rows.

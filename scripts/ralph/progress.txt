## Iteration 2 - US-010: Redact generic secret-like substrings
- What I did: Added _GENERIC_LABELED_SECRET regex `(?i)(\b(?:key|token|secret|password)\b\W*)[A-Za-z0-9_\-]{20,}` to praxis/redactor.py and wired it into the redaction pipeline with replacement `\1[REDACTED]` so the label + separator survive and only the high-entropy tail is redacted. Generalized _PROVIDER_PATTERNS into _PATTERNS as a tuple of (pattern, replacement) pairs so the new entry can carry its own backref-using replacement while redact_secrets() remains a single fold. Added 9 tests covering all four labels (key/token/secret/password), case-insensitive matching, short-value non-match, label-inside-word non-match, intervening-word non-match, and a self-test that two passes produce the same output.
- Files changed: praxis/redactor.py, tests/test_redactor.py, scripts/ralph/feature/secret-redaction/prd.json (US-010 -> passes:true).
- Verification:
  - uv run pytest -q  -> 54 passed (was 45; +9 new US-010 tests).
  - uv run mypy praxis/redactor.py tests/test_redactor.py  -> Success: no issues.
  - uv run mypy praxis  -> still 34 pre-existing errors in 6 files, zero new.
- What the next iteration should know:
  - Module-level pattern list is now `_PATTERNS: tuple[tuple[re.Pattern[str], str], ...]` (not `_PROVIDER_PATTERNS`). If US-011 wants to add another rule, append `(compiled_pattern, replacement_string)` to this tuple; the replacement may contain backrefs.
  - Idempotence (US-011) is already de facto preserved: provider regexes have no `[` in their char classes, and the new _GENERIC_LABELED_SECRET value class also excludes `[` (and the {20,} length defeats the 8-char `REDACTED` body), so a second pass over `[REDACTED]` cannot match. Verified by test_generic_does_not_re_redact_placeholder. US-011 should add an explicit `redact_secrets(redact_secrets(x)) == redact_secrets(x)` test (and probably one with multiple secret types in the same string) to lock this in, but no code change is needed unless that test fails.
  - The labeled-secret regex uses `\W*` (zero-or-more non-word chars) as the separator. This deliberately includes `\n`, so multi-line `key:\n  abc...` patterns are still redacted; but intervening English words (e.g., "password is wrong") break the match because the next `\w` stops `\W*` and the value class doesn't admit a leading letter-word. Keep this property when extending.
  - The literal alternation is exactly `key|token|secret|password` -- singular, no plurals, no compound forms like `API_KEY` (since `\bKEY\b` does not match inside `API_KEY`). If a future story wants to cover compound env-var names, that is a new requirement; do not silently widen this regex.

## Iteration 6 - US-043: Significant-slope gate using stderr
- What I did: Added praxis/behavior/slope.py implementing the v0.2 trajectory model's stage 2 (PRAXIS_V0_2_SPEC.md section 7.2). Public surface: `SlopeFit` (slope, stderr, n, plus `significant` property), `WeeklyTrajectoryFit` (engagement/delegation/independence SlopeFits + per-dim SlopeFit dict), `fit_metric(buckets, getter)`, `fit_weekly_trajectory(buckets)`, and the two spec constants `SIGNIFICANCE_STDERR_MULTIPLIER=1.5` and `SIGNIFICANCE_MIN_SLOPE_PER_WEEK=0.05`. Fit math is the textbook simple linear regression with `SE(slope) = sqrt(SSR/(n-2)/Sxx)`; n<2 or degenerate-x returns `SlopeFit(0,0,n)`; n==2 returns exact slope with stderr=0 (no residual df). Only `eligible_for_fit` buckets contribute. The x-axis is whole-week offset from the earliest eligible bucket (since `week_start` is always Monday, `(start_i - anchor_start).days / 7` is integral and gap weeks read as a real week-2 offset, not bucket-index 1). `fit_metric` also drops buckets where the getter returns None, which is how per-dim fits respect the "skip-not-invent" contract from US-042. Wired the new names into praxis/behavior/__init__.py.
- Files changed: praxis/behavior/slope.py (new), praxis/behavior/__init__.py (export new names), tests/test_slope.py (new, 29 tests), scripts/ralph/feature/trajectory-model/prd.json (US-043 -> passes:true).
- Verification:
  - uv run pytest -q  -> 102 passed (was 73; +29 new tests in test_slope.py).
  - uv run --with mypy mypy --follow-imports=silent praxis/behavior/slope.py tests/test_slope.py  -> Success: no issues found in 2 source files.
  - uv run --with mypy mypy praxis  -> 52 errors across 5 pre-existing files (trajectory.py, advisor.py, aggregate.py, coach.py, judge.py); zero in slope.py or __init__.py. Same convention as US-042.
- What the next iteration should know:
  - Public API for downstream stories: `from praxis.behavior import SlopeFit, WeeklyTrajectoryFit, fit_metric, fit_weekly_trajectory, SIGNIFICANCE_STDERR_MULTIPLIER, SIGNIFICANCE_MIN_SLOPE_PER_WEEK`. US-044 (labels) should call `fit_weekly_trajectory(buckets)` once and read `.engagement.significant`, `.delegation.significant`, and (for the label-table sign branches) `.engagement.slope`, `.delegation.slope`. The signs you need are spec 7.2 rows: engagement up vs flat vs down, delegation up vs flat vs down; "flat" == not significant.
  - US-045 hysteresis uses a different multiplier: `2.0 * stderr` instead of `1.5 * stderr`. Do NOT bake that into `SlopeFit.significant`. Add a separate predicate at the labeling layer (e.g. `is_strongly_significant(fit) = abs(fit.slope) >= 2.0 * fit.stderr and abs(fit.slope) >= 0.05`). The current `significant` property is the 1.5-multiplier gate from US-043 only.
  - The "fewer than 4 weekly buckets" -> "Reading" label (US-044) is enforced by counting eligible buckets. Each SlopeFit carries `n`, which is the count of eligible buckets that contributed to that fit. For rate metrics (engagement/delegation/independence), `n` equals the eligible-bucket count of the input. For dim metrics it can be lower because some buckets may not report a dim key; use the engagement fit's `n` (or compute `len([b for b in buckets if b.eligible_for_fit])`) for the global "4 buckets" gate, not the per-dim n.
  - Boundary semantics of `significant`: `>=` on both conditions (inclusive). The tests pin this with slope=0.75 / stderr=0.5 (both exact in IEEE 754, so `1.5 * 0.5 == 0.75` and the comparison is unambiguous). If you write new boundary tests, pick values that are exact in float (powers of 2, 0.5, 0.25, 0.75) - I tried 0.15/0.10 first and `1.5*0.10` rounded to 0.15000000000000002, which made the boundary appear non-inclusive in float space. The implementation is correct; the test inputs just need to be representable.
  - `_least_squares` returns `SlopeFit(0, 0, n)` (with the actual n!) for degenerate cases (n<2 or all-equal x). That means callers can still tell "I had 1 bucket" from "I had 0 buckets" if they ever need to, even though the fit is meaningless either way. The label code in US-044 should not look at n for the empty-vs-singleton distinction - it should look at the count of eligible buckets directly.
  - Why I didn't compute a confidence interval / p-value: the spec only asks for slope and stderr and the two thresholds. Bringing in scipy or hand-coding a t-distribution would add a dependency and code surface for no spec-required win. If a later story needs a CI, add it as a new helper on top of SlopeFit; do not retrofit it here.
  - `partial(_get_dim, key)` is used (not a default-arg lambda) for the per-dim getters to keep mypy happy with the `Callable[[WeeklyBucket], float | None]` signature on `fit_metric`. If you add another per-key fit (e.g. per-task-cluster), follow the same pattern: a top-level `_get_x(key, b)` function plus `partial(_get_x, k)`.
  - Don't fix the 52 pre-existing mypy errors as part of this PRD - they're in v0.1 modules (advisor, coach, judge, aggregate, trajectory) untouched by US-042/043. "Typecheck passes" continues to mean "zero new errors in the files this story added".

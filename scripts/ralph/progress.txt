## Iteration 3 - US-072: --dry-run computes without persisting
- What I did: Added `dry_run: bool = False` parameter to run_weekly(). When True it gates the entire persistence block (no ProfileStore construction, no save_weekly_digest call) and propagates `dry_run=True` as a keyword arg through to _step_render so the future on-disk file write can be short-circuited. Explicit `store=` injection does NOT override `dry_run` - the gate is "if not dry_run", so passing a real store + dry_run=True still writes nothing. The pipeline (scan/cluster/pass1/pass2/validate/select/follow_up/render) still executes in full so terminal output is computed and returned in WeeklyRunSummary.rendered_terminal.
- Files changed: praxis/orchestrator.py, tests/test_orchestrator.py
- Verification: `uv run pytest` -> 709 passed (was 703 before; +6 new tests for US-072). `uv run mypy praxis` -> 34 errors in 6 files, none in orchestrator.py (same baseline as US-070/US-071).
- What the next iteration should know:
  - _step_render now accepts a `dry_run` keyword-only arg (default False). The signature is `(sessions, tasks, selection, follow_up, snapshot, *, dry_run=False)`. The positional-args count is still 5, so the US-070 data-flow contract test (test_run_weekly_step_inputs_match_documented_upstream) is intact. US-073 (perf) and the eventual render-file-write story should both honor this kwarg: when dry_run is True, skip the on-disk html_path write but still return the rendered_terminal string.
  - The dry_run contract is "no side effects, ever". Even if a caller passes `store=my_store, dry_run=True`, no write happens. This is enforced in run_weekly's `if not dry_run:` block - keep this gate, do not move the save_weekly_digest call outside it.
  - test_run_weekly_dry_run_does_not_create_db_file is the canonical guard against accidentally constructing ProfileStore() in the dry-run path. ProfileStore.__init__ does `home.mkdir(...)` + `_init_schema()` which writes ~/.praxis/profile.db. The test asserts that file does not exist after a dry-run on a fresh tmp_home. If you ever need a read-only store handle in run_weekly, you'll need a separate "read-only" construction path, or do the reads through a passed-in store the caller already has.
  - There is no weekly CLI command yet. When `praxis weekly` lands, it should expose `--dry-run` as an argparse flag and pass it through to run_weekly(dry_run=...). The daily CLI's `praxis scan` does NOT need a dry-run today (out of scope for this story).
  - cost_total_usd and cost_baseline_usd are still passed through as None - that is US-073's job. The dry-run path does not even reach the save call so these fields' values do not matter when dry_run=True.

## Iteration 4 - US-073: Performance target on 30-session week
- What I did: Built praxis/scoring/cost.py with estimate_weekly_pipeline_cost() that sums per-call USD estimates across cluster + pass1 + pass2 + selector (using model-card per-million pricing and a chars/4 ~= tokens heuristic). Plumbed it into run_weekly: cost_total_usd is now populated (None when estimate <= 0.0), and cost_baseline_usd comes from new ProfileStore.weekly_cost_baseline(before_week_iso, lookback_days=90) which AVG()s prior weekly_digests rows over the last 90 days, excluding the current week. Baseline read is gated by the same `if not dry_run` block so dry-run never touches the DB. Added a perf test that writes 30 synthetic Claude JSONL files into tmp_home (mtimes spread across the past week so the default since_days=7 picks them up), stubs score_session / cluster_sessions / select_moments_with_fallback with realistic-shaped responses, runs run_weekly(), and asserts wall<120s + cost_total<$2 + prints the measurement.
- Files changed: praxis/scoring/cost.py (new), praxis/orchestrator.py, praxis/storage/profile_store.py, tests/test_orchestrator.py
- Verification: `uv run pytest` -> 714 passed (was 709 before; +5 new tests for US-073). `uv run mypy praxis` -> 34 errors in 6 files, none in orchestrator.py / cost.py / profile_store.py (same baseline as US-070/US-071/US-072). Perf-test measurement on this dev machine: wall_elapsed=0.008s, cost_total_usd=$0.3250 -- well under both gates.
- What the next iteration should know:
  - The cost figures are PROJECTIONS, not invoiced spend. The estimator's chars/4 -> tokens conversion is the industry rough-cut and the model-card per-million rates assume standard (non-cached, non-batch) pricing. The spec section 10.2 disclaimer "rough estimate from token volume + tier pricing" applies. Do not present cost_total_usd as a real bill; the cost-ledger renderer in spec 10.1 needs that disclaimer rendered once at the bottom of the HTML digest.
  - estimate_weekly_pipeline_cost() takes (sessions, pass1_results, pass2_results, moment_count, cheap_model_id="claude-haiku-4-5"). The cheap_model_id default matches spec 5.2 / 4.3's "cheap-tier model from the user's primary provider" for Anthropic users; switch to "gpt-5-mini" when the runtime is OpenAI-primary. The estimate is conservative either way (the two cheap-tier prices land within ~10% of each other).
  - The follow-up step is currently template-based (no LLM call), so estimate_weekly_pipeline_cost() does NOT include a follow-up wedge. If a future story adds an LLM call to follow_up, plumb its cost through this function and update the docstring comment.
  - ProfileStore.weekly_cost_baseline() returns None when no prior digest in the lookback window has a non-NULL cost_total_usd. Renderers SHOULD treat that as the "--" case (spec 8.4 baseline-forming language; the cost ledger should mirror it). Do NOT default to 0.0 - that would hide first-time and migration scenarios.
  - The perf test's stubs deliberately seed a low_confidence rate of ~20% (every 5th session by stable_id hash) so pass 2 actually runs and contributes to the cost estimate. If you raise/lower this, the stubbed cost estimate will move; the test's $2 ceiling has plenty of headroom but the literal numbers in progress.txt will change.
  - The cost estimator reads judge_model off each JudgeResult, so it correctly bills pass1 against the cheap tier and pass2 against the frontier IF those calls used the right model. Right now both _step_pass1 and _step_pass2 call score_one_session which defaults to claude-opus-4-7 for both passes (a known limitation from US-070). When the batched cheap-tier pass1 lands, the cost numbers will drop noticeably; expect cost_total_usd to fall ~3x in production.
  - There is no model-cost test for unpriced models (Copilot, anything without input_per_million_usd). The estimator returns 0.0 for those calls. If a future story adds tracking for unpriced models (e.g. via subscription minute-budgets), wire it through estimate_call_cost rather than adding a parallel path - keep one place where cost flows.

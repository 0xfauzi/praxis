## Iteration 2 - US-010: Redact generic secret-like substrings
- What I did: Added _GENERIC_LABELED_SECRET regex `(?i)(\b(?:key|token|secret|password)\b\W*)[A-Za-z0-9_\-]{20,}` to praxis/redactor.py and wired it into the redaction pipeline with replacement `\1[REDACTED]` so the label + separator survive and only the high-entropy tail is redacted. Generalized _PROVIDER_PATTERNS into _PATTERNS as a tuple of (pattern, replacement) pairs so the new entry can carry its own backref-using replacement while redact_secrets() remains a single fold. Added 9 tests covering all four labels (key/token/secret/password), case-insensitive matching, short-value non-match, label-inside-word non-match, intervening-word non-match, and a self-test that two passes produce the same output.
- Files changed: praxis/redactor.py, tests/test_redactor.py, scripts/ralph/feature/secret-redaction/prd.json (US-010 -> passes:true).
- Verification:
  - uv run pytest -q  -> 54 passed (was 45; +9 new US-010 tests).
  - uv run mypy praxis/redactor.py tests/test_redactor.py  -> Success: no issues.
  - uv run mypy praxis  -> still 34 pre-existing errors in 6 files, zero new.
- What the next iteration should know:
  - Module-level pattern list is now `_PATTERNS: tuple[tuple[re.Pattern[str], str], ...]` (not `_PROVIDER_PATTERNS`). If US-011 wants to add another rule, append `(compiled_pattern, replacement_string)` to this tuple; the replacement may contain backrefs.
  - Idempotence (US-011) is already de facto preserved: provider regexes have no `[` in their char classes, and the new _GENERIC_LABELED_SECRET value class also excludes `[` (and the {20,} length defeats the 8-char `REDACTED` body), so a second pass over `[REDACTED]` cannot match. Verified by test_generic_does_not_re_redact_placeholder. US-011 should add an explicit `redact_secrets(redact_secrets(x)) == redact_secrets(x)` test (and probably one with multiple secret types in the same string) to lock this in, but no code change is needed unless that test fails.
  - The labeled-secret regex uses `\W*` (zero-or-more non-word chars) as the separator. This deliberately includes `\n`, so multi-line `key:\n  abc...` patterns are still redacted; but intervening English words (e.g., "password is wrong") break the match because the next `\w` stops `\W*` and the value class doesn't admit a leading letter-word. Keep this property when extending.
  - The literal alternation is exactly `key|token|secret|password` -- singular, no plurals, no compound forms like `API_KEY` (since `\bKEY\b` does not match inside `API_KEY`). If a future story wants to cover compound env-var names, that is a new requirement; do not silently widen this regex.

## Iteration 3 - US-011: Redaction is idempotent
- What I did: Added 6 tests at the end of tests/test_redactor.py that lock in idempotence: a per-pattern double-run check across all 6 entries in _PATTERNS, a mixed-secrets double-run check, and four placeholder-stability checks (bare placeholder, placeholder in prose, two adjacent placeholders, placeholder right after a label). No change to praxis/redactor.py -- idempotence was already a design invariant of the existing regexes (value classes exclude `[`, labeled-secret tail requires >= 20 chars > len("REDACTED")=8, and "REDACTED" is not a label literal); the new tests just assert it.
- Files changed: tests/test_redactor.py, scripts/ralph/feature/secret-redaction/prd.json (US-011 -> passes:true).
- Verification:

  - uv run mypy praxis  -> still 34 pre-existing errors in 6 files, zero new.
- What the next iteration should know:
  - All three feature stories (US-009, US-010, US-011) now pass. If the PRD has no further stories, the loop should terminate.
  - Idempotence is now a tested invariant, not just a design intent. If a future change to praxis/redactor.py adds a pattern, the new pattern MUST keep `[` out of its value class and its tail-length budget; otherwise test_bare_placeholder_is_unchanged / test_placeholder_in_prose_is_unchanged will fail loudly.
  - The "redaction is idempotent" property is what lets the rest of the pipeline call redact_secrets() defensively at multiple stages (e.g., on read, on write, on render) without risk of corrupting already-redacted text. Spec section 4.4 calls for this; future code that wires redaction into persistence/rendering paths can rely on it.

## Iteration 5 - US-033: Compute 90-day rolling baseline per dim from session_scores
- What I did: Added praxis/scoring/baseline.py with two frozen dataclasses (BaselineInputSession, Baseline) and a pure compute_baseline(sessions, as_of=None) function. Window is [as_of_date - 90 days, current ISO week Monday) - the current ISO week is excluded by computing the Monday of as_of's week and using it as the exclusive upper bound. Each session's overall is clipped to [1.0, 9.0] before averaging; the 6 rubric dim scores plus engagement/delegation/independence rates are averaged as-is. Sessions are weighted equally because BaselineInputSession deliberately has no length field. Added 13 tests in tests/test_baseline.py covering: empty input, window bounds, ISO-week-Monday math (Wednesday/Monday/Sunday), current-week exclusion (Tuesday + Monday boundary), >90-day exclusion, the 90-day-edge inclusive boundary, overall clipping (high + low outliers), the "dim scores are NOT clipped" inverse, the full 6-dim average, the three rate averages, the no-length-weighting design lock, default as_of, and dataclass immutability.
- Files changed: praxis/scoring/baseline.py (new), tests/test_baseline.py (new), scripts/ralph/feature/baseline-stats/prd.json (US-033 -> passes:true).
- Verification:
  - uv run pytest -q  -> 73 passed (was 60; +13 new baseline tests).
  - uv run mypy praxis/scoring/baseline.py tests/test_baseline.py  -> Success: no issues.
  - uv run mypy praxis  -> still 34 pre-existing errors in 6 files (29 source files checked, +1 for the new baseline.py which has zero errors). Zero new errors introduced.
- What the next iteration should know:
  - Public API: from praxis.scoring.baseline import compute_baseline, Baseline, BaselineInputSession. Also exported: BASELINE_WINDOW_DAYS (90), OVERALL_CLIP_LOW (1.0), OVERALL_CLIP_HIGH (9.0), and the private _iso_week_start helper that tests import directly.
  - compute_baseline() is PURE - no I/O, no DB. It takes a list of BaselineInputSession (a plain dataclass with started_at, overall, dimension_scores, engagement_rate, delegation_rate, independence_rate) and returns a Baseline. Wiring this into the actual weekly digest pipeline (reading from profile.db, computing signals on the fly since engagement/delegation/independence are NOT stored in session_scores today, calling redactor, etc.) is deliberately deferred. Future stories should build BaselineInputSession instances at the call site.
  - The window math: window_end is exclusive (the Monday of as_of's ISO week); window_start is inclusive (as_of_date - 90 days). A session exactly 90 days before as_of IS included; a session at Monday 00:00 of the current week is EXCLUDED. This is what "excluding the current ISO week" means in the spec.
  - All means are pre-rounded inside compute_baseline: dim/overall to 2 decimals (matches ProfileSnapshot.from_scores in praxis/scoring/aggregate.py), rates to 4 decimals (matches trajectory.py). Don't round again at the call site; if a future story needs raw precision it should change this in one place.
  - Empty / no-sessions-in-window state returns a Baseline with session_count=0 and all means=0.0. This is the signal US-035 will key off ("if less than 14 days of available data, render baseline as '--'"). The 14-day check needs the calendar-day span of all available sessions, not just the in-window count - that lookup lives outside compute_baseline and should be passed to whichever component renders the panel.
  - For US-034 (significance gating, |delta| < 0.3 -> '~'): the gate operates on this_week_value - baseline.dimension_means[k] on the /10 scale, so it can be implemented as a small pure helper that takes (current, baseline_value) -> ('~' | formatted_signed_string). Apply uniformly in both HTML and terminal renderers. The relevant existing renderers are praxis/reports/html_report.py and praxis/reports/terminal.py - they currently render dimension scores without baselines (see _dimension_bar_html in html_report.py line 47), so US-034 will be the first story that introduces the baseline+delta row.
  - For US-036 (last-week annotation): the same window-end Monday computed here is also "last week's window_end + 7 days" target. Either reuse _iso_week_start or add a companion compute_last_week_mean(sessions, as_of) function. The HTML faded secondary annotation lives on the dim row; the terminal omits it entirely (spec 8.1).
  - Tests use a fixed AS_OF = datetime(2026,5,27,12,0,UTC), a Wednesday. Reuse this approach in future tests so the current ISO week is unambiguous (Monday = 2026-05-25) and you don't get flaky tests around month/year boundaries.

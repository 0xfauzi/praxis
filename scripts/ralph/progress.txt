## Iteration 6 - US-043: Significant-slope gate using stderr
- What I did: Added praxis/behavior/slope.py implementing the v0.2 trajectory model's stage 2 (PRAXIS_V0_2_SPEC.md section 7.2). Public surface: `SlopeFit` (slope, stderr, n, plus `significant` property), `WeeklyTrajectoryFit` (engagement/delegation/independence SlopeFits + per-dim SlopeFit dict), `fit_metric(buckets, getter)`, `fit_weekly_trajectory(buckets)`, and the two spec constants `SIGNIFICANCE_STDERR_MULTIPLIER=1.5` and `SIGNIFICANCE_MIN_SLOPE_PER_WEEK=0.05`. Fit math is the textbook simple linear regression with `SE(slope) = sqrt(SSR/(n-2)/Sxx)`; n<2 or degenerate-x returns `SlopeFit(0,0,n)`; n==2 returns exact slope with stderr=0 (no residual df). Only `eligible_for_fit` buckets contribute. The x-axis is whole-week offset from the earliest eligible bucket (since `week_start` is always Monday, `(start_i - anchor_start).days / 7` is integral and gap weeks read as a real week-2 offset, not bucket-index 1). `fit_metric` also drops buckets where the getter returns None, which is how per-dim fits respect the "skip-not-invent" contract from US-042. Wired the new names into praxis/behavior/__init__.py.
- Files changed: praxis/behavior/slope.py (new), praxis/behavior/__init__.py (export new names), tests/test_slope.py (new, 29 tests), scripts/ralph/feature/trajectory-model/prd.json (US-043 -> passes:true).

- What the next iteration should know:
  - Public API for downstream stories: `from praxis.behavior import SlopeFit, WeeklyTrajectoryFit, fit_metric, fit_weekly_trajectory, SIGNIFICANCE_STDERR_MULTIPLIER, SIGNIFICANCE_MIN_SLOPE_PER_WEEK`. US-044 (labels) should call `fit_weekly_trajectory(buckets)` once and read `.engagement.significant`, `.delegation.significant`, and (for the label-table sign branches) `.engagement.slope`, `.delegation.slope`. The signs you need are spec 7.2 rows: engagement up vs flat vs down, delegation up vs flat vs down; "flat" == not significant.
  - US-045 hysteresis uses a different multiplier: `2.0 * stderr` instead of `1.5 * stderr`. Do NOT bake that into `SlopeFit.significant`. Add a separate predicate at the labeling layer (e.g. `is_strongly_significant(fit) = abs(fit.slope) >= 2.0 * fit.stderr and abs(fit.slope) >= 0.05`). The current `significant` property is the 1.5-multiplier gate from US-043 only.
  - The "fewer than 4 weekly buckets" -> "Reading" label (US-044) is enforced by counting eligible buckets. Each SlopeFit carries `n`, which is the count of eligible buckets that contributed to that fit. For rate metrics (engagement/delegation/independence), `n` equals the eligible-bucket count of the input. For dim metrics it can be lower because some buckets may not report a dim key; use the engagement fit's `n` (or compute `len([b for b in buckets if b.eligible_for_fit])`) for the global "4 buckets" gate, not the per-dim n.
  - Boundary semantics of `significant`: `>=` on both conditions (inclusive). The tests pin this with slope=0.75 / stderr=0.5 (both exact in IEEE 754, so `1.5 * 0.5 == 0.75` and the comparison is unambiguous). If you write new boundary tests, pick values that are exact in float (powers of 2, 0.5, 0.25, 0.75) - I tried 0.15/0.10 first and `1.5*0.10` rounded to 0.15000000000000002, which made the boundary appear non-inclusive in float space. The implementation is correct; the test inputs just need to be representable.
  - `_least_squares` returns `SlopeFit(0, 0, n)` (with the actual n!) for degenerate cases (n<2 or all-equal x). That means callers can still tell "I had 1 bucket" from "I had 0 buckets" if they ever need to, even though the fit is meaningless either way. The label code in US-044 should not look at n for the empty-vs-singleton distinction - it should look at the count of eligible buckets directly.
  - Why I didn't compute a confidence interval / p-value: the spec only asks for slope and stderr and the two thresholds. Bringing in scipy or hand-coding a t-distribution would add a dependency and code surface for no spec-required win. If a later story needs a CI, add it as a new helper on top of SlopeFit; do not retrofit it here.
  - `partial(_get_dim, key)` is used (not a default-arg lambda) for the per-dim getters to keep mypy happy with the `Callable[[WeeklyBucket], float | None]` signature on `fit_metric`. If you add another per-key fit (e.g. per-task-cluster), follow the same pattern: a top-level `_get_x(key, b)` function plus `partial(_get_x, k)`.

## Iteration 8 - US-045: Hysteresis on label transitions
- What I did: Extended praxis/behavior/labels.py with the spec 7.4 hysteresis layer on top of the US-044 label table. Added `HYSTERESIS_STDERR_MULTIPLIER=2.0`, `is_strongly_significant(SlopeFit) -> bool` (same shape as `SlopeFit.significant` but with the 2.0 multiplier; the 0.05/week floor is unchanged), `apply_hysteresis(eligible_count, fit, previous_label)`, and `label_trajectory_with_hysteresis(buckets, previous_label=None)`. The hysteresis rule: return the naive (1.5-gate) label when (a) `previous_label is None` (cold start), (b) naive == previous (no change to gate), or (c) the transition crosses the Reading boundary (data-availability change, not slope direction). Otherwise the naive change is accepted iff `is_strongly_significant(fit.engagement) or is_strongly_significant(fit.delegation)` - at least one of the labeling axes clears 2.0*stderr - else the previous label is retained. This makes the function a fix-point operator: AC #3 ("no change on identical input") falls out as a consequence, not a special case.

I went with (i) because it matches the US-044 progress-notes plan ("is_strongly_significant(fit.engagement_or_delegation)"), matches the natural reading "|slope| >= 2.0*stderr on the relevant axis" as an existence test, and does not require persisting prev's fit. If the spec author later wants (ii), they would need to thread `previous_fit: WeeklyTrajectoryFit | None` through `apply_hysteresis` and the storage layer would need to persist per-week fits, not just labels. Right now we only need prev's label.
  - **Reading is a hysteresis-bypass label, not a hysteresis-gated label.** The Reading <-> non-Reading transition is driven by bucket count (data availability), not by slope direction, so spec 7.4 hysteresis does not apply to it. Concretely: if eligible_count drops below 4, the label becomes Reading even if prev was Learning; conversely, when eligible_count first crosses >=4, the naive label is accepted even if no axis is strongly significant. test_apply_hysteresis_reading_to_x_passes_through and test_apply_hysteresis_x_to_reading_passes_through lock this in. If a future story argues for hysteresis on Reading transitions too, that is a spec change, not a bug fix.
  - **Fix-point property is structural, not just tested.** apply_hysteresis is constructed so that running it twice on the same (buckets, label) pair always returns the same label. Specifically: in the accept branch we return the naive label, and on a re-run prev becomes that naive label so we hit the "naive == prev" early return; in the retain branch we return prev, and on a re-run naive is unchanged so we hit the same retain branch and return prev again. Don't add branches that break this without a corresponding two-run stability test.
  - **Boundary tests use exact-in-float magnitudes.** Same rationale as test_slope.py / test_labels.py: |slope|=2.0*stderr is checked with slope=1.0, stderr=0.5 (both representable exactly in IEEE 754) so the `>=` boundary is unambiguous. _WEAK_UP/_DOWN (slope=0.75, stderr=0.5) sit at exactly 1.5*stderr - inside the 1.5 gate, outside the 2.0 gate. _STRONG_UP/_DOWN (slope=1.0, stderr=0.5) sit at exactly 2.0*stderr. If you add new boundary tests, follow the same pattern; values like 0.3 or 0.1 will round to non-representable floats and make `>=` boundary assertions fragile.
  - **0.05/week floor is shared, multiplier is not.** is_strongly_significant uses the same `SIGNIFICANCE_MIN_SLOPE_PER_WEEK=0.05` floor as `SlopeFit.significant`. Only the stderr multiplier (2.0 vs 1.5) tightens. test_is_strongly_significant_requires_min_slope_per_week and test_is_strongly_significant_at_min_slope_boundary_is_inclusive pin this. If US-046 adds another threshold (e.g. for headline copy), follow the same separation: import SIGNIFICANCE_MIN_SLOPE_PER_WEEK from praxis.behavior.slope and reuse it instead of redefining 0.05.
  - **No storage / orchestrator wiring yet.** US-045 ships the pure-function hysteresis logic; the spec-wide concern of "where do we read previous_label from" (SQLite digest table per spec section 14) is out of scope for this PRD. When that wiring lands, the call site is one line: `previous_label = digest_repo.get_previous_label(...)`; then `label = label_trajectory_with_hysteresis(buckets, previous_label)`. Don't add a `LabelStore` dataclass or a stateful wrapper in this module - the orchestrator owns persistence, this module owns math.
